# Unit test gap analysis

Use this reference for **Phase 1** of `test-dev`. The goal is to ensure every public function in the in-scope files has at least one test covering its happy path, plus tests for the obvious edge cases its body implies.

## 1. Enumerate the public surface

For each in-scope file, list its public/exported symbols. The notion of "public" is language-specific:

- **Go**: identifiers starting with an uppercase letter — `func Foo`, `type Bar struct`, `func (b *Bar) Baz`. Also: `func init` is implicit and does not need a direct test.
- **TypeScript / JavaScript**: anything with `export` / `export default`. For React, exported components and hooks.
- **Python**: anything not prefixed with `_` at module top-level, plus class methods not prefixed with `_`.
- **Rust**: `pub` / `pub(crate)` items.
- **Java/Kotlin**: `public` / `internal` (Kotlin) members.

When in doubt, inspect call sites: if anything outside the file/module imports the symbol, treat it as public.

Skip:
- Generated code (look for headers like `// Code generated by ... DO NOT EDIT.`).
- Test helpers and fixtures (files matching `*_test.*`, `tests/`, `__tests__/`, etc.).
- Pure type/interface declarations with no behavior.

## 2. Map symbols to existing tests

For each public symbol, find any existing test that covers it:

- Search the test files for the symbol name (`Grep` is usually enough).
- For methods, also search the receiver type with the method.
- For HTTP handlers/routes, search by route path or handler name.
- For React components, search by component name in `*.test.tsx` / `*.spec.tsx`.

A symbol is **covered** if at least one test invokes it on a non-error happy path.

A symbol is a **gap** if either:
- No test references it, or
- Only error-path / setup tests reference it without exercising the success path.

## 3. Inspect the body for missed branches

Even a "covered" symbol may have obvious untested branches. Scan the body for:

- **Error returns** — does each `return err` / `throw` / `Err(...)` have a test that triggers it?
- **Nil / empty inputs** — slices, maps, strings, pointers, optional values.
- **Boundary values** — first/last index, zero, max int, exact-equal vs greater-than, time-on-boundary.
- **Switch / match arms** — every case at least once.
- **`select` / channel / goroutine paths** (Go) — done channels, default branches.
- **Retries, timeouts, backoff** — at least one test per terminal state (success, max retries, ctx cancel).
- **Context cancellation** — if the function takes `ctx`, a cancelled-ctx test.

Flag each missed branch as its own gap.

## 4. Fill each gap

This skill is test-code-only (`SKILL.md` Global Rule 6). Production source is read-only here. The flow per gap:

1. **Write the test** asserting the desired behavior derived from existing contracts (function signatures, doc comments, type definitions, surrounding tests). Run it.
2. **Test passes immediately** → the path now has explicit coverage. Done.
3. **Test fails AND the failure shows the test itself is wrong** (you misstated the expected behavior, the fixture is malformed, the mock is misconfigured) → adjust the test until it expresses the correct expectation. This is the only freely-allowed correction.
4. **Test fails AND the test correctly expresses the intended behavior** → this is a suspected business-logic defect. Do **not** edit production code. Record the defect for the final summary (file:line of the production code, the test path, observed vs expected behavior in one sentence), leave the failing test in place, and move to the next gap. If leaving it red blocks the rest of the suite from running, skip it with the framework's standard mechanism (`t.Skip`, `it.skip`, `@pytest.mark.skip`) annotated with a comment pointing to the suspected defect.
5. **Refactor the test** — clean up duplicated setup, share fixtures with the surrounding tests, keep names consistent.

Each edge case is its own mini cycle. Do not bundle multiple unrelated edge cases into one test function.

## 5. Style-matching checklist

Before writing each new test, confirm:

- File location matches the project (Go: same package + `_test.go`; TS: `*.test.ts(x)` next to source or under `__tests__/`; Python: `tests/` or `test_*.py`).
- Naming matches existing tests (`TestFooBar_NilInput`, `describe('FooBar', () => it('returns ... when ...'`)`, etc.).
- Use the same assertion library/helpers already in the project (no new `testify` if the project uses stdlib `testing`; no new `chai` if Jest is the convention).
- Use the same mocking style (interface fakes vs gomock vs jest.mock, etc.).
- Table-driven where the existing tests are table-driven; one test per case where they're not.

## 6. Verify

Run the project's lint + unit suite. Examples:

```bash
# Go:    go vet ./... && go test ./...
# Node:  npm run lint && npm test
# Python: ruff check . && pytest
# Rust:  cargo clippy --all-targets && cargo test
```

All must pass before moving to Phase 2. If anything fails, follow Error Recovery in `SKILL.md`.

## 7. What to record for the summary

Track per-file:

- Public symbols enumerated.
- Symbols that were already covered (count, no detail needed).
- Gaps found and filled (count + the test file paths).
- Gaps where the test had to be adjusted because the initial expected behavior was wrong (count, no detail needed unless surprising).
- **Suspected business-logic defects** discovered while filling gaps — production file:line, the test path, observed vs expected behavior in one sentence, whether the test was left red or skipped. These feed the central defect list reported at the end of the skill.
